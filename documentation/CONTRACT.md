# Evidence sidecar contract v1

The atlas manifest and regional `site.json` may reference a local, immutable evidence JSON sidecar by path and checksum using their eventual extension mechanism. The engine consumes the sidecar directly. Asset keys must match the source registry and lineage ledger. The sidecar can accompany either a global atlas or a site pack. It owns no raster or downloader.

| Record | Producer obligations |
| --- | --- |
| Package | Set `schema_version` to 1, stable `package_id` and immutable `version`. Declare datasets, source products, footprints and any modality inventory scopes. Empty lists are valid and represent unknown coverage without further authority. |
| Dataset | Supply stable `id`, mission, instrument, modality, product class, archive URL, dataset version and catalogue status. Use the configured modality keys for summary inclusion. |
| Product | Reuse a stable asset ID and pin version, source URL, processing level and readiness. Preserve source CRS or null, variable IDs, separate native sampling and verified effective feature scale (metres), acquisition UTC interval where known, optional independently verified compatibility key, limitations and provenance. Multiple windows of a product may be separate footprints. Set `observation_extent_complete` and `support_extent_complete` only for exhaustive geometry of the respective kind for this immutable asset, including any derivative window limits. Both default to false. |
| Footprint | Link to the product ID. Preserve the geometry source URL and transform status, and set `coverage_kind` to `observation` or `usable_support`. Valid support represents the actual support relevant to all advertised variables, including nodata/quality and stencil exclusions where needed. Split by product/variable record if support differs. A usable product may have both an acquisition outline and separate verified usable support. Use unknown/invalid states when necessary. |
| Inventory | A complete inventory is a producer assertion that all in-scope catalogue products were searched and represented for one modality, within the declared geographic scope, source set and revision. Pin its scope, dataset IDs, source URL and authority note. Completeness is relative to the package's declared source universe. An omitted/incomplete inventory cannot establish absence. |
| Model requirement | Supply variable, allowed product classes, allowed modalities if relevant, maximum native spacing and/or effective scale in metres where the calculation needs them, allowed processing levels if applicable and optional UTC acquisition window. Candidate products must have usable readiness and support. Full request support is required. Use a compatibility key only for audited, co-registered products with suitable references/units for the declared model. |

Geometry uses GeoJSON-like **shape syntax** with explicit Mars metadata. Positions are `[longitude, latitude]` in degrees. Query geometries already use planetocentric latitude and east-positive longitude and accept signed or unsigned longitudes. Footprint geometries use either source geographic coordinates declared by `source_crs` with `native_geographic` status or the canonical conventions with `canonical_verified` and a transform record. Unknown source CRS is quarantined. Projected source coordinates require upstream verification/reprojection. All edges follow shorter great-circle arcs after normalization. Prepare sufficient vertices for curved/native pixel boundaries. Multipolygon pieces can be bounded independently. Use the explicit `Global` shape only for independently verified whole-sphere applicability. Large footprints should be split into bounded pieces. Identical duplicate IDs are deduplicated, conflicting duplicates and dangling references reject the package, and invalid/unknown geometry is quarantined. A support completeness assertion requires at least one valid support record. An observation completeness assertion requires at least one valid footprint and no unresolved footprint records. A verified support shape also counts as observed geography.

Wire schemas are generated from the runtime types. Python callers use the same models and functions. Outputs report method/config IDs, normalized cells, evidence fractions, bound endpoints, states and provenance. A resolved model result authorizes use of its declared evidence under this contract. The caller remains responsible for pack release gates, vertical transformations, variable units and the numerical calculation. Scores describe documentation only and are never part of the route cost API.


## Catalogue scope and compatibility

A complete modality scope must list the full dataset set for that modality in the package. Those datasets must declare complete catalogue metadata. Scopes can be unioned and a partially searched query narrows the upper bound only within its searched part. A known product with unlocated or non-exhaustive observation geometry can keep coverage unknown even inside a complete inventory. Catalogue closure and geometry closure are separate. An explicitly complete, authoritative scope may have zero datasets when the scoped source universe was searched and none applied.

Capability requests use shorter great-circle line segments, a bounded polygon or a point. Corridor width is the **full** width in metres, and omission uses length coverage. A numeric coverage fraction can describe the union of qualified products. A variable is eligible only when one verified product or prepared derivative covers the full query. A calculation requiring several variables needs one product or a shared audited `compatibility_key`. Evidence at adjacent or disconnected locations cannot satisfy one route. The acquisition window must contain the product's complete declared acquisition interval. The contract treats missing scale, processing or temporal evidence as unsupported whenever requested.

## Pipeline handoff

1. Reuse the asset ID and version from the source registry. When a registry row such as the blueprint's `ctx` covers both terrain and optical assets, export separate product IDs and carry their shared registry relationship in provenance.
2. Attach source labels, Mars reference metadata, original geometry identifiers, and the transform recipe. Supply canonical prepared shapes for projected rasters and retain the native CRS in the product. Coordinates in a native geographic footprint require declared latitude type, longitude direction and domain, with native spheroid axes for planetographic latitude.
3. Export observation footprints separately from support derived from valid pixels, quality masks and any needed analytical stencil. Emit separate products for differing variable masks. Use `needs_preprocessing` or `unknown` until support has been checked. Report bounds and raster spacing independently from effective scale.
4. Validate the evidence sidecar against the [package schema](schemas/evidence-package.v1.schema.json), validate references through `DocumentationEngine` on pack load, and pin the sidecar checksum in the pack/atlas manifest extension. Validate downstream requests with the [query schema](schemas/capability-query.v1.schema.json).
5. The runtime adapter can expose `summarize(cell_id)` for Atlas inspection and call `resolve(request)` before applying routing or scientific pack gates. Load a package once and reuse its footprint index. The presentation layer should convert longitude to its signed display domain and keep the uncertainty and provenance visible.
