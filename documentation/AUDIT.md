# Return Window documentation engine audit

The Return Window source is an editable architecture and offline atlas. Its Python ingestion and FastAPI runtime are proposed. The separate Martian Map delivery is a compiled browser build with regional terrain binaries and JSON, while Senula's prototype routes over synthetic terrain. The existing boundaries are the blueprint's `registry → footprint-index → availability`, `atlas-manifest`, `lineage`, regional `site.json` and `routing-inputs`. The Zod schemas validate the editor and Atlas, and currently contain no operational footprint package. Use a versioned JSON evidence sidecar referencing the same asset IDs and leave both manifests in place.

| Recommendation | Assessment and implementation decision |
| --- | --- |
| HEALPix NESTED | The library supplies the equal-area spherical index, hierarchy and sampled boundaries. Adopt 128 as a configurable display-summary default, subject to subset benchmarks. Its 196,608 cells are ~734.3 km² on a 3,389.5 km sphere. [HEALPix](https://healpix.sourceforge.io/) · [Astropy HEALPix](https://docs.astropy.org/projects/astropy-healpix/en/latest/api/astropy_healpix.HEALPix.html) · [JPL radii](https://ssd.jpl.nasa.gov/planets/phys_par.html) |
| Coordinate conventions | USGS documents both planetocentric/east and planetographic/west. Use the report's [0,360) storage inside the engine and preserve the editor's ±180 display. Use source radii for latitude conversions, preserve source CRS and verified frame transforms, and use the JPL volumetric radius only for engine spherical measurements. The Atlas's 3,396,190 m radius is its scale-bar/reference convention. [USGS Mars coordinates](https://planetarynames.wr.usgs.gov/Page/MARS/system) |
| Scale | Global grid size controls summary units; source pixel/post spacing describes sampling; effective scale describes resolved detail; local request geometry/stencil defines analytical support; display tiles have their own resampling. Neither MOLA gridding nor the Atlas's relief layer establishes local slope support. [PDS MEGDR](https://pds-geosciences.wustl.edu/missions/mgs/megdr.html) |
| Two axes and modality utility | Preserve coverage and readiness independently. Use the maximum utility of overlapping products and report support area separately from observed area. Use explicit, equal modality weights in the first config. Keep optional sampling ramps separate from model resolution checks. Readiness stays categorical and verified usable support is the lower-bound gate. Tiers and weights are engineering conventions. |
| Unknown metadata | A complete dataset inventory does not establish complete modality coverage across arbitrary archives. Require a declared authoritative modality inventory scope and keep unlocated/invalid evidence unknown. Score intervals describe catalogue/readiness uncertainty under the stated method. |
| Local eligibility | Check actual usable support, type, variable, processing, sampling and any requested effective scale/time independently of cell scores. Require explicit compatibility for cross-product combinations. NASA PDS footprints can describe acquisition areas or tracks. A HiRISE image and a stereo DTM are separate products. [PDS footprints](https://ode.rsl.wustl.edu/mars/pagehelp/Content/Frequently_Asked_Questions/Product_Footprints.htm) · [HiRISE DTMs](https://www.uahirise.org/dtm/) |
| Area and topology | Use great-circle arcs for prepared footprints. Mars-sphere gnomonic topology avoids longitude seams and poles. Measure overlay geometry back on the sphere. HEALPix edges are curved and are approximated by sampled chords. Bounded geometries avoid the projection horizon. [PROJ gnomonic](https://proj.org/en/stable/operations/projections/gnom.html) · [PROJ geodesic area](https://pyproj4.github.io/pyproj/stable/api/geod.html) |

The report is a proposal. Its downloaded citation tokens and dates do not establish current challenge requirements. The engine has no dependency on the challenge resource-release timing. The challenge detail endpoint could not be fetched during initial verification. NASA's event site gives November 14–15. [NASA Space Apps](https://www.spaceappschallenge.org/about/)

## Implementation sequence and ownership

1. Freeze one normalized evidence sidecar and one model request with runtime validation and generated JSON Schema. Yumeth owns source selection, acquisition, labels, original and transformed CRS, nodata/quality masks, data packages and catalogue completeness. The engine verifies supported inputs, quarantines unusable geometry and produces evidence summaries.
2. Implement the Mars grid, bounded spherical overlay and versioned score. Keep support, discovery and completeness separate. No map renderer, mobility, ranking, or science-interest coupling.
3. Verify local point, polygon and route decisions, explicit fallbacks and source lineage. Pack owners still own stencil, vertical datum, release gate and physical calculation checks. For the source-backed demo, prefer Yumeth's existing Jezero 20 m CTX window and cross-check the authoritative archive with byte-range reads. [USGS Jezero products](https://astrogeology.usgs.gov/search/map/mars-2020-jezero-crater-landing-site-products)
4. Benchmark NSIDE 64 and 128 with measured subset timings and memory before deciding on planetary batch processing. Preserve the Atlas and the original workspace; integrate at the manifest and runtime boundaries after the package producer adopts the contract.
